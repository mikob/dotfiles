# Continuous issue fixing in fresh contexts

Use this procedure only in coordinator mode. A worker assigned one issue must not create its own issue-dispatch loop.

## Establish one coordinator

Resolve the repository from the invocation's current working directory using the main skill. Save its canonical GitHub identity and absolute checkout path so later checks cannot drift to another repository. In Codex, call `list_projects` and match the repository to its saved project. If a required project or tool is unavailable, report that specific blocker rather than choosing another project or pretending work was scheduled.

Create or reuse one thread heartbeat for this repository's coordinator using the available `automation_update` tool. Request a one-minute cadence and verify the returned schedule. Keep the coordinator in its existing task; create a new task only when there is a new issue to work on, not on every empty poll. Do not substitute an hour-long schedule or a shell sleep loop if one-minute scheduling is unsupported; report the limitation.

The saved scheduler prompt must identify this skill and coordinator mode, repository identity and path, project ID, issue selection constraints, state record, and automation ID once known. It must instruct every wakeup to inspect worker state before dispatching, stay quiet while nothing actionable has changed, and stop when the user cancels the loop. Use the scheduling tool rather than hand-editing automation configuration. Local execution requires the computer and app to remain running.

Keep durable coordinator state in its task and saved automation prompt, outside the code changes: active issue, dispatch state, worker task/host IDs, last status cursor, known issue outcomes and PR links, and current blockers. Reuse this record on every wakeup. If a coordinator for the same repository is already active, reuse it rather than running competing dispatchers.

## Check, select, and dispatch

1. On the initial invocation, inspect the backlog immediately. On subsequent one-minute wakeups, inspect the active worker first. Use a compact `wait_threads` snapshot when available. Queued setup, active implementation, awaiting approval, and awaiting clarification all occupy the single worker slot. A task ending a turn with a question is not a completed issue. Do not dispatch another issue while that slot is occupied, and do not accelerate the worker's hourly GitHub clarification checks to once per minute.
2. When the worker reports completion, verify its issue/PR outcome, record it, and release the slot. A verified regular or draft PR ends that worker's assignment; it does not have to be merged before the next issue starts. Preserve the worker task for replies and review. If a worker failed, lost access, or stopped without a credible result, retain its blocker and task instead of retrying it in a fresh context every minute. Resume that same issue task when new information makes progress possible.
3. When idle, list open issues oldest first following the main skill, including already-existing backlog items as well as newly opened issues. Inspect linked PRs and the coordinator's recorded outcomes before selecting. An issue with a live PR from an earlier worker remains covered even if GitHub still shows it open. Do not create a second fix for that issue. A closed, unmerged PR or an earlier failed attempt needs changed evidence or user direction before retrying; retain the existing task and outcome rather than silently restarting it.
4. If no eligible issue exists, leave the one-minute heartbeat active and return quietly. If an issue is selected, record a pending dispatch for its repository/issue key before creating the worker. Reconcile an uncertain task-creation response against existing tasks before retrying. A queued `clientThreadId` still reserves the worker slot and must not be used as a ready `threadId`.
5. Create a new Codex project task with `create_thread`. Use the matched project ID and an isolated worktree when `isGitRepository` is true. Use a new task, not a fork containing prior conversation history, and do not reuse a completed issue's task for a different issue. Preserve default model settings unless the user chose otherwise. The worker must fetch and branch from the selected `dev`, `main`, or `master` remote base before editing, even if initial worktree setup used another checkout state; never create a missing `dev` branch to avoid the specified fallback order.
6. Give the worker a self-contained prompt: exact repository and issue URL, the absolute skill path, **single-issue worker mode**, selected base or the `dev` → `main` → `master` selection rule, user constraints, and relevant issue facts. Explicitly require fetching current code, creating a task branch, attempting and testing the fix, and creating/verifying a PR. Include the clarification behavior: ask the same question in the new worker task and GitHub issue together, use the first response, and check GitHub hourly while awaiting an answer. Require the final issue, branch, PR, validation, and blocker report. Tell it not to select another issue or start a coordinator. Transfer relevant facts and decisions, not the preceding workers' transcripts.
7. Record the ready worker's task and host IDs, or reconcile queued setup before monitoring it. Track the worker until it completes or needs input, and report meaningful outcomes in the coordinator. Every new issue gets its own fresh task; clarification and follow-up on the same issue return to that issue's existing task.

## Completion and stopping

After a worker finishes, the next idle scheduler wakeup checks the backlog again. Continue this serial loop until the user stops it; an empty backlog is an idle state, not completion. Disable the coordinator heartbeat on cancellation and handle any active worker according to the user's cancellation scope. End each worker's hourly clarification monitor when its own assignment ends. Preserve branches, worktrees, and PRs rather than deleting them as incidental cleanup.

Do not merge PRs or run deployments as part of the loop. Report failures requiring user action, and do not repeatedly create workers or post the same notification while a blocker remains unchanged.
